# 31. Non-functional acceptance: security, performance, availability, usability, operations (SRS section 7)

## How non-functional requirements are accepted
Business users cannot judge encryption or throughput by clicking, so the SRS assigns each non-functional requirement a verification method: **Test** (measure it), **Inspection** (look at configuration, documents or evidence), **Demo** or **Analysis** (reasoned evidence from specialists). The UAT lead collects the evidence, attaches it to the case, and the relevant owner (security lead, operations lead, QA lead) signs. A case passes only when the evidence is current, dated, and from the environment under acceptance (a laptop result is not a production-like result).

> Evidence rule: every case below says *what to attach*. "Trust me" and screenshots without dates are not evidence. A case with no evidence is Blocked, not Passed.

@term SLO / SLA = Service level objective / agreement: the measured level of availability or speed promised.
@term RPO / RTO = Recovery point objective (maximum data loss) / recovery time objective (maximum downtime).
@term PITR = Point-in-time recovery: restoring the database to a chosen moment.
@term SIEM = Central security log and alert system.
@term SBOM = Software bill of materials: list of all components in a build.
@term WCAG = Web content accessibility guidelines.

## 31.1 Security (SRS 7.3)
@release R1

@case T-NFR-01 | All traffic uses TLS 1.2+ with HSTS | R1 | NFR-SEC-01, EI-CM-01 | UAT
1. Run a TLS scan against the web, API, portal and sync endpoints.
2. Try plain HTTP and TLS 1.0/1.1.
=> Only TLS 1.2 or 1.3 is accepted; HTTP redirects or is refused; public endpoints send HSTS. Attach the scan report with date.

@case T-NFR-02 | Data is encrypted at rest; bank details and personal identifiers have field-level encryption | R1 | NFR-SEC-02 | UAT, ADM
1. Inspect the storage encryption settings (database, object store, backups).
2. As the schema owner in a test copy, read the bank account column of a supplier directly.
=> Storage encryption is on. The column shows ciphertext, not the account number. Attach settings evidence and the query result.

@case T-NFR-03 | OWASP ASVS Level 2, and Level 3 for authentication, approvals, payments and administration | R1 | NFR-SEC-03 | UAT
1. Review the ASVS applicability matrix and the evidence for each requirement.
=> Every ASVS L2 item (and L3 for the named areas) is marked met, not applicable (with reason) or an accepted risk signed by the security lead. No unreviewed items.

@case T-NFR-04 | The approval-signing key is in an HSM or cloud KMS; no secrets in source or client code | R1 | NFR-SEC-04 | UAT, ADM
1. Inspect the key ceremony record and KMS/HSM configuration.
2. Run the secret scan on the repository and a search of the web client bundle for keys.
=> The signing key cannot be exported and is used only by the isolated signer; other secrets come from a vault and have a rotation record; the scans find none.

@case T-NFR-05 | The pipeline runs SAST, dependency scanning, secret scanning, checksum verification and SBOM, and signs images | R1 | NFR-SEC-05 | UAT
1. Open the latest release pipeline results.
=> All five checks ran on the release candidate commit and passed or have recorded exceptions; the SBOM exists; the container images are signed and the signature verifies.

@case T-NFR-06 | Automated cross-tenant and privilege-escalation probes run in CI | R1 | NFR-SEC-06, ISO-T01 | UAT
1. Open the last probe run for the release candidate.
=> Probes ran as the tenant database login and as the schema owner, covering cross-tenant, cross-project and export attempts; zero successes. Denials appear in the audit entries.

@case T-NFR-07 | The independent penetration test has closed all critical and high findings | R1 | NFR-SEC-07 | UAT
1. Obtain the penetration-test report and the retest letter.
=> No open critical or high finding; each closed finding has retest evidence; the test is dated within the last 12 months. Required before general availability.

@case T-NFR-08 | Security logs go to the SIEM, with alerts, and never contain secrets | R1 | NFR-SEC-08 | UAT, ADM
1. After running this manual, search the central logs for the test passwords, MFA codes, tokens and bank account numbers.
2. Trigger an account lockout and a bulk export; look for the alerts.
=> No secret or bank number appears in logs. Both events produced a SIEM alert with correlation identifiers.

@case T-NFR-09 | ISO/IEC 27001 and SOC 2 Type II plan | R1 | NFR-SEC-10 | UAT
1. Review the certification plan.
=> A dated plan with milestones within 18 months of general availability, with an assigned owner. (Should, evidence of plan only.)

@case T-NFR-14 | Financial and tax treatment signed by a qualified professional | R1 | NFR-PRV-05 | FIN, UAT

## 31.4 Availability, reliability and recovery (SRS 7.2)
@release R1

@case T-NFR-21 | Availability target and service-level reporting | R1 | NFR-AVL-01 | UAT
1. Review the monitoring set-up and the first month's availability report (or the design analysis before launch).
=> 99.9% monthly target (99.5% in the first six months) is defined with a measurement method, exclusions and alerts.

@case T-NFR-22 | Point-in-time restore meets 5 minutes RPO and 4 hours RTO, and the restored system verifies | R1 | NFR-AVL-02, NFR-AVL-05, OPS-T01 | UAT, ADM, AUD
1. Note the time and the total of a known set of documents. Make a further change (the "last committed" transaction).
2. Simulate loss of the primary database.
3. Restore to a point immediately before the loss, using the documented runbook, and time the whole exercise.
4. In the restored system run the audit-chain verification, the integrity scan and the stock/AP/AR reconciliations.
=> Data loss is within 5 minutes; total restoration time is within the 4-hour (or 1-hour premium) target.
=> Chain verification, integrity scan and reconciliations all report zero differences. A signed drill record is produced.

@case T-NFR-23 | A failure mid-command leaves it fully committed or fully rolled back; replay is safe | R1 | NFR-AVL-03, AUD-02 | UAT
1. With a test hook, kill the application process in the middle of approving a journal; restart.
2. Repeat the same request with the same idempotency key.
=> After restart the journal is either fully approved with its audit record and event, or not at all; the replay completes it once.

@case T-NFR-24 | Reporting, AI, notification, export and integration failures do not stop transactions | R1 | NFR-AVL-04 | UAT
1. Stop the reporting service, the AI service and the notification service in turn; keep posting transactions.
=> Transactions continue unaffected; the admin health view shows the failed service; queued items process after recovery. (Related T-INT-06.)

@case T-NFR-25 | Backups are encrypted, copied off-site in object-locked storage, and restore-tested quarterly | R1 | NFR-AVL-05 | UAT, ADM
1. Inspect the backup configuration and the off-site bucket (object lock, encryption).
2. Review the last quarterly restore-test record.
3. Try to delete an off-site backup with the operational credentials.
=> Backups are encrypted and retained off-site in isolated object-locked storage; deletion is refused; a signed restore-test record exists within the last 90 days (SRS 9.1).

@case T-NFR-26 | Deployments and migrations are backward-compatible: no downtime in working hours | R1 | NFR-AVL-06, NFR-MNT-02 | UAT
1. During a session with users working, deploy the next build with an additive migration.
=> No user is logged out or sees errors; in-flight commands complete; the migration list shows only additive changes with checksums.

## 31.5 Usability, accessibility and localisation (SRS 7.5)
@release R1

@case T-NFR-27 | WCAG 2.1 AA and full keyboard use | R1 | NFR-USB-01 | UAT, SITE
1. Run the automated accessibility scan on the key screens (requisition, PO, journal, IPC, dashboard).
2. Without using the mouse, create and submit a requisition and approve a PO.
3. Use a screen reader on one form.
=> No failures at level AA; every function reachable by keyboard with visible focus; the screen reader announces fields, errors and status.

@case T-NFR-28 | A clerk can work a standard document after one day of training | R1 | NFR-USB-02 | AP, STORE, SITE
1. Give three first-time users (an AP clerk, a storekeeper and a site engineer) one day of training from the in-product help.
2. The next morning each performs their standard document (invoice, goods receipt, requisition) alone, timed and observed.
=> At least 2 of the 3 complete it without help from the observer, with no data errors. Record times and stumbling points.

@case T-NFR-29 | Layouts adapt from desktop to tablet and phone; approvals and dashboards are fully usable on a phone | R1 | NFR-USB-03 | PM, EXE
1. On a phone-size screen open the inbox, approve a requisition, view the executive dashboard and a cost report.
=> No horizontal scrolling in the page frame, tap targets are usable, and every approval step including MFA works.

@case T-NFR-30 | Ethiopic script and calendars render correctly everywhere | R1 | NFR-USB-04, NFR-USB-05, ADM-04 | ADM, FIN
1. Create a supplier named in Amharic; show it on screen, in PDF, Word and Excel exports and in an email notification.
2. Switch the date display between Gregorian and Ethiopian.
=> The name renders correctly in all places; dates display in both calendars; stored values do not change; default time zone is Africa/Addis_Ababa.

@case T-NFR-31 | Every refusal explains the rule and the action that would satisfy it | R1 | NFR-USB-06, EI-UI-02 | UAT
1. Gather all refusals recorded in this test run (budget, SoD, closed period, hold point, duplicate, mismatch, conflict, permission).
2. Score each on five points: no change occurred; names the rule; names the next step; audited; same outcome by a second route.
=> All refusals score 5/5. Any refusal scoring lower is raised as a Medium defect.

@case T-NFR-32 | One documented design system across web, mobile and portals | R1 | NFR-USB-07 | UAT
1. Compare the same functions on web, mobile and portal against the design-system documentation.
=> Components, colours, typography and patterns match the documented system; deviations are listed and accepted.

## 31.7 Data integrity (SRS 7.7)
@release R1

@case T-NFR-40 | Exact decimal arithmetic with defined rounding and allocation | R1 | NFR-DAT-03, FIN-01, PRC-06 | FIN, UAT
1. Split 100.00 equally across three cost codes.
2. Allocate 1,700,000 across two items by value (T-PRC-06 numbers).
3. Enter a document with two lines of 0.10 and 0.20 and read its total.
=> The split of 100.00 is 33.34, 33.33, 33.33 (or the documented largest-remainder order) and sums exactly to 100.00. Allocations always sum to the original amount. Totals are exactly 0.30, never 0.30000000000000004.

@case T-NFR-41 | Financial, contractual and audit records are never hard-deleted | R1 | NFR-DAT-02 | UAT
1. Try to delete a posted invoice, a signed contract, an approved IPC and an audit entry through the screen and the API.
=> All are refused; cancellations and reversals leave visible records.
